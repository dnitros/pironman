# Generalize daemon shutdown into hooks, drained against in-flight IPC connections

The daemon manages hardware whose state must be left off when the daemon exits — starting with the RGB strip, with fan and OLED control planned. We considered wiring each hardware component's shutdown call directly into `runDaemon`, and considered guarding a shutdown call with the same per-handler mutex the RGB IPC handlers use to serialize their persist-then-hardware-write sequence. Both tie shutdown behavior to a single component and don't generalize to hardware added later. We chose a generic `shutdownHooks ...func() error` list, run by `serveDaemon` once `ipc.Server.Serve` returns, so adding a new component's shutdown is one more closure at the call site. `Serve` itself now drains in-flight IPC connections with a `sync.WaitGroup` before returning, guaranteeing no handler — and the hardware write it makes — is still running when the hooks fire; this bounds shutdown latency to the existing per-connection I/O timeout. A hook's own failure is logged rather than treated as fatal, so it doesn't block the daemon from exiting or block later hooks from running.
